## 一、文档目的与范围

本架构设计书定义忆联 MVP 三端产品（C 端 App、B 端机构后台、平台后台管理）的技术架构，覆盖技术选型、系统架构、数据模型、API 设计、AI 集成、安全与合规、部署运维、测试策略与开发里程碑。

目标：在 22 周试点计划内，以最小成本交付可运行、可审计、可扩展的 MVP，并为后续 AI 能力（声音克隆、影像生成等）预留扩展空间。

## 二、设计原则

- 简单优先：MVP 用单体分层架构 + 容器化部署，不提前引入微服务。
- 部署自主：云厂商与机房由用户自行部署决定，架构保持云中立（S3 兼容存储、自选推送、Docker Compose 可移植）。
- 数据合规：部署位置与数据处理遵守境内合规要求；LLM 使用 DeepSeek API，按服务条款执行数据使用约定。
- 三端一致：C 端 App、B 端 Web、后台管理 Web 共享同一套 API 契约。
- 审计完备：用户、机构、后台三侧敏感操作全部留痕。
- 扩展预留：故事问答接 DeepSeek API；声音克隆、影像生成等后续能力以独立服务形态接入。

### 5.1 分层说明

- 客户端层：三端通过统一 API 访问服务端；C 端 App（Flutter）当前包含登录注册、记忆档案、成员主页、口述历史、我的素材与记录、联系家人、消息中心、家族关系图谱等页面；内置图片/音频上传；支付暂不做（试点期以机构渠道结算为主）。
- 接入层：CDN 加速静态资源；WAF 防护；API Gateway 做统一鉴权、限流与审计。
- 应用层：Spring Boot 单体按领域分包（user、lovedone、family、connection、notification、qa、consent、audit、invite、album、event、partner、admin），模块间通过内部接口解耦，为后续拆分微服务留边界。
- 数据层：PostgreSQL 存业务与审计数据；Redis 存会话、限流、队列；对象存储（S3 兼容）存照片/录音/视频/纪念册，CDN 分发。
- AI 集成：故事问答通过 Spring WebClient 调用 DeepSeek API（OpenAI 兼容端点），SSE 流式输出经 SseEmitter 转发，输入输出均经过安全过滤，所有交互记录入库。

设计要点：

- **渲染与业务解耦**：`ShareAssetService` 只做"取数据 → 套模板 → 出图 → 存对象存储"，模板用 SVG 便于中文排版与版本迭代；

- **每次分享都可归因**：海报二维码与分享链接统一走 `short_links`，落地页访问写 `share_events`，用于计算扫码转化率与 K 因子；
- **AI 标识**：AI 修复/上色的图片在水印与元数据中标注"AI 修复"；
- **限额与降级**：图像增强按用户与家族配额（试点期每人每月 N 次），超限提示而非报错。

### 6.2 数据规则

- 故人数据必须绑定"创建者"与授权成员；机构只能关联订单与引导记录，不可关联隐私素材内容。

### 6.3 家族关系与消息模型（V1.5 新增，对应 Flyway V10）

关系行 `family_relationships` 表示两人之间的**技术关系**（自动建立），是否展示由双方各自确认决定：

| 字段 | 语义 |
| --- | --- |
| relation_a_to_b | B 是 A 的谁（A 确认后才有值，可空） |
| relation_b_to_a | A 是 B 的谁（B 确认后才有值，可空） |
| a_status / b_status | 各自一侧状态：PENDING / ACTIVE / REJECTED |
| a_confirmed_at / b_confirmed_at | 各自确认时间 |
| status | 整行状态：ACTIVE / REMOVED（解除关系） |

可见性判定集中在 `RelationshipVisibility`：

- `relationFromMe(rel, me)` 非空 ⇔ 我这一侧 ACTIVE 且我给出称谓，且整行未 REMOVED；
- "对方是我的谁 / 我是对方的谁"分别取自己一侧与对方一侧，对方未确认时返回 null；
- 记忆档案列表、关系列表、关系图谱统一复用该判定，避免各处重复实现。

入族扇出（`NotificationService.fanoutOnJoin`）：

1. 计算双方"家族网络"：`circleOf(user)` = 自己 + 所在家族全部成员 + 已确认关系的联系人；`networkOf(user)` 在 circleOf 基础上做广度优先遍历，得到整个连通图（跨家族，避免家族成为孤岛）；
2. 建立两类关系：①新人 × 对方网络的每位成员；②对方（邀请人/发起人）× 新人网络的每位成员。已 REMOVED 的行复活为双方 PENDING，复用历史行避免重复记录；
3. 已知方向直接置 ACTIVE（邀请码场景：邀请人一侧；建立联系场景：双方各自的声明）；
4. 其余待确认方向写入 `notifications`，双方各一条，`suggested_relation` 仅作预填建议；已存在未处理消息时不重复推送（幂等）。
5. 规模保护：`networkOf` 遍历节点数超过 `MAX_NETWORK_SIZE`（200）时退回一跳 `circleOf`，避免一次入族产生海量消息；实测三跳网络（大山→小云→小河→小月）通知完整覆盖。

确认后的一致性（`ensureSharedFamily`）：任一方确认关系时，若双方尚无共同家族，则自动把确认方加入对方的本人档案所在家族（`family_members.relation_source = RELATION_CONFIRM`，VIEWER 权限），保证"确认了就能在记忆档案里看到对方"。解除关系时同步回收由关系产生的成员关系（`CONNECTION_REQUEST` / `RELATION_CONFIRM`）。

消息状态机：UNREAD → READ（打开列表）/ ACTIONED（确认）/ REJECTED（拒绝）；确认与拒绝均写审计日志（`RELATION_CONFIRMED` / `RELATION_REJECTED`）。账号注销时级联删除本人相关消息及其关联关系上的消息，避免外键悬挂。

关系图谱查询（`GET /api/v1/connections/graph`）：

| 参数 | 作用 |
| --- | --- |
| includePending | 是否包含"待确认/我已拒绝"节点（应用端默认关闭，开启后半透明展示） |
| includeExtended | 是否包含"家人的家人"二级节点（应用端默认关闭，虚线展示） |

二级节点（`extended=true`）由"我已确认的家人所确认的家人"推导，附带 `viaUserId` / `viaUserName` / `relationFromVia`（关系路径，如"张耘嫣的母亲"）与 `requestPending`（我已发起建立联系）。隐私边界：二级节点**只返回姓名与关系路径**，不返回出生年月/籍贯/性别，也不能通过档案接口访问其资料；建立关系仍需双方同意（复用 `POST /api/v1/connections/requests`）。

### 6.4 关系存储选型：PostgreSQL 关系表（D8，2026-09-10 确认）

**结论：不引入 Neo4j（或其他图数据库），关系图继续用 PostgreSQL 的 `family_relationships` 关系表存储，查询时由应用层实时组装。**

现行查询形态与量级：

| 查询 | 实现方式 | 量级 |
| --- | --- | --- |
| 以我为中心的直接关系（深度 1） | `user_a_id` / `user_b_id` 两次索引扫描 | 家族几十人 |
| 双方"家族圈子"（两跳） | 若干 IN 查询（`NotificationService.circleOf`） | 试点期 50-100 个家庭，全库边数 10³~10⁴ |
| 图谱可见性 | 运行时按 `a_status` / `b_status` 计算，不落库 | - |

不引入图库的原因（成本 > 当前收益）：

1. **双写一致性**：PostgreSQL 是事实来源（外键、事务、审计日志、注销级联删除、72h 物理删除 SLA）。引入图库后每次关系/成员变更都要同步，跨库无本地事务，需要 outbox 或 CDC + 补偿任务，存在数据漂移风险。
2. **合规删除成本翻倍**：永久删除（含备份）必须在两个存储同时保证。
3. **权限与审计仍在关系库**：可见性依赖 `family_members` 与关系两侧状态，图库无法替代，反而多一层跨库 join 或同步。
4. **运维负担**：用户自行部署（D1/D6），多一个 JVM 服务 + 备份/升级/监控；社区版集群等能力受限。
5. **建模收益有限**：当前模型是"点对点关系 + 两侧各自确认"，用两列表达两侧称谓已足够；亲属称谓推导属业务规则，换库不减少代码量。

改用图库的触发条件（满足任意一条再评估）：

- 多跳亲属推导成为核心功能（任意两人的关系推导 / 最短亲属路径），且需在 10⁴~10⁵ 条边上实时查询；
- 出现图算法需求（家族社群发现、相似家族推荐、中心度等）；
- 遍历类查询成为主要负载，PostgreSQL 递归 CTE 无法满足（通常在 10⁷ 量级边才明显）。

迁移路径：先在 PostgreSQL 内用 `WITH RECURSIVE` 实现 2-3 跳推导（零新增组件）→ 触及瓶颈后再引入 Neo4j 或 Apache AGE（PostgreSQL 图扩展），采用 outbox 模式异步同步，避免在线双写。

## 七、API 设计

- 风格：REST + JSON，统一前缀 /api/v1。
- 契约：OpenAPI 3.0 文档随代码维护（springdoc-openapi），前后端按契约联调。
- 统一响应：{ code, message, data }；错误码分段：1xxx 认证、2xxx 参数、3xxx 业务、4xxx 权限、5xxx 系统。
- 鉴权：JWT（Access + Refresh），Spring Security 实现；后台管理额外 TOTP 双因素。
- 限流：普通接口每用户 60 req/min；故事问答 10 req/min；机构结算接口按机构限流。
- 幂等：订单、删除请求等写操作带幂等键。
- 主要接口见 PRD 第十三章，开发前输出完整 OpenAPI 文档。

## 八、AI 集成设计（故事问答）

### 8.1 调用链路

用户提问 → 输入安全过滤（敏感词/自伤/诈骗识别）→ 记忆检索（结构化检索：故人资料、家族故事）→ 组装提示词（风格配置）→ 调用 DeepSeek API（deepseek-v4-flash，流式输出）→ 输出二次过滤 → 生成"AI 标识"与对话记录 → 返回客户端。

### 8.2 技术实现

- 使用 Spring WebClient 调用 DeepSeek OpenAI 兼容端点，支持超时、重试与连接池。
- SSE 流式输出：服务端通过 SseEmitter / StreamingResponseBody 转发给客户端；用户取消时通过 context 停止模型调用。
- 安全过滤以 Spring Interceptor/Filter 实现，输入输出双重校验。
- 高频问题走 Redis 缓存；超时或失败降级为模板化回复。

### 8.3 延迟预算（目标 <15 秒）

| 环节 | 预算 |
| --- | --- |
| 网络与鉴权 | 0.2 秒 |
| 输入安全过滤 | 0.1 秒 |
| 记忆检索 | 0.2 秒 |
| LLM 生成（流式） | 8-12 秒 |
| 输出过滤与返回 | 0.3 秒 |

### 8.4 合规要点

- 使用 DeepSeek API，按服务条款确认用户对话数据不用于模型训练。
- 未成年人账号拒绝调用问答接口。
- 连续使用超 2 小时提醒；极端情绪触发安抚话术与求助入口。
- 所有问答记录入库，后台可检索复核；不当内容拦截 100%（人工复核兜底）。
- 上线前完成安全评估与算法备案准备（与开发并行）。

## 九、安全与合规架构

- 传输与存储：全链路 TLS 1.2+；对象存储服务端加密；敏感字段数据库加密；密码 BCryptPasswordEncoder。
- 认证与权限：Spring Security + JWT + 刷新令牌；后台 TOTP；用户/机构/后台三套权限模型。
- 机构隔离：partner_staff 只能访问本机构数据；隐私素材内容默认不可见。
- 未成年人保护：实名年龄核验；14 岁以下需监护人同意；未成年人账号不开放故事问答。
- 删除合规：删除工单 72 小时 SLA、双人复核；级联清理对象存储、数据库与备份。
- 审计：查询、导出、删除、审核、结算等敏感操作全部写 audit_logs。
- 深度合成预留：后续声音/影像能力上线前补齐授权记录、AI 标识与用途限制。

### 10.1 环境规划

### 10.2 构建与 CI/CD

- Maven 构建（mvn verify），springdoc-openapi 生成 API 文档。
- 提交 → 静态检查与单元测试 → 构建 Docker 镜像（Eclipse Temurin JRE 基础镜像）→ 部署 staging → 人工验收 → 灰度发布 → 生产。
- 功能开关支持远程启停（故事问答、纪念册模板等）。

### 10.3 监控与告警

- 指标：接口成功率/延迟、故事问答延迟、队列积压、存储用量、DeepSeek API 成本、JVM 内存。
- 日志：业务日志、审计日志、AI 调用日志。
- 告警：错误率、延迟、删除工单 SLA 超期、结算异常。

### 10.4 备份与恢复

- PostgreSQL 每日全量 + 实时 WAL；对象存储冗余备份；每月恢复演练。

### 10.5 成本控制

- MVP 以 2-3 台 4GB 规格 ECS/自托管主机 + 独立数据库起步（JVM 预留 512MB-1GB/实例）；静态资源走 CDN；问答按需调用并缓存；素材分级存储（热/冷）。

### 10.6 自行部署说明

- 云厂商、机房与域名由用户自行决定；本架构保持可移植：Docker Compose 编排、S3 兼容存储抽象、推送与短信配置化。
- 正式部署手册（含环境变量、备份、扩容、HTTPS 证书）在 MVP 开发期（W8 前后）输出。
